00 · Executive summary

Two pages were added to fill operational gaps the rest of the platform did not address:

  • Deploys — backend, frontend, and mobile engineers need a single place to drop a build artifact, write a short changelog, and surface it to managers. The page records every upload with file metadata, environment (production / staging / preview), status (ready / deprecated / rolled-back), and an expandable bullet changelog. The most recent upload is rendered as a hero card; everything older sits on a vertical timeline.
  • Reminders — subscriptions, SSL certificates, cloud reservations, domain registrations, anything with an expiry date the team needs to track. The page lets managers create a reminder with multiple "notify me before" intervals and renders each as an urgency-driven countdown card whose color shifts from green to red as the expiry approaches.

Both modules ship as UI-only: they read from in-memory seed data via Zustand stores and persist nothing between page reloads. The backend integration plan is included in section 04.

1.8 Changelog component

Used identically inside the hero card and every timeline card. Renders as a flat list under the rest of the card content.

Bullet rendering

Each change is one <li>: a 1×1 primary-colored dot (margin-top tuned to align with the first line of text), then the text in text-xs text-text-secondary leading-relaxed.

Initial visible window

By default, only the first 2 bullets are visible. If the deploy has 3 or more changes, a "Show N more" button appears below the list (where N = changes.length − 2).

Show / Collapse toggle

A small text button with a ChevronDown icon. Clicking it adds the deploy's id to a Set<string> stored in expanded state at the page level. The chevron rotates 180° via rotate-180 conditional class when expanded. The button label switches between "Show N more" and "Collapse".

Empty-changes guard

If changes.length === 0, the entire block returns null. Submitting an upload with no bullets is normalized to ["No changelog provided"] by the dialog, so this edge is rare.

1.9.8 Submit behavior

On click of "Submit Deploy":

  1. Generates a new id: "dep-" + Math.random().toString(36).slice(2, 10).
  2. Constructs a DeployInterface using the form fields + the authenticated user as uploaded_by.
  3. Captures a Blob URL via URL.createObjectURL(file); stores it on download_url so the Download button can re-deliver the file later in the session.
  4. Calls addDeploy(newDeploy) on the store; the new entry lands at index 0.
  5. Calls onOpenChange(false) to close the modal.

1.9.9 Reset on close

A useEffect watching open clears all form state (file, title, version, changes, environment, isDragging) whenever the dialog closes — so opening it again starts fresh.

1.12 Helper functions

formatSize(bytes)

const formatSize = (bytes: number): string => {
    if (bytes < 1024) return `${bytes} B`;
    if (bytes < 1024 ** 2) return `${(bytes / 1024).toFixed(1)} KB`;
    if (bytes < 1024 ** 3) return `${(bytes / 1024 ** 2).toFixed(2)} MB`;
    return `${(bytes / 1024 ** 3).toFixed(2)} GB`;
};

Used for the per-deploy file size and the Total Size stat.

relativeTime(iso)

const relativeTime = (iso: string): string => {
    const diffMs = Date.now() - new Date(iso).getTime();
    const mins = Math.floor(diffMs / 60_000);
    if (mins < 1) return "just now";
    if (mins < 60) return `${mins} min ago`;
    const hours = Math.floor(mins / 60);
    if (hours < 24) return `${hours}h ago`;
    const days = Math.floor(hours / 24);
    if (days < 30) return `${days}d ago`;
    const months = Math.floor(days / 30);
    return `${months}mo ago`;
};

Output buckets: "just now", "X min ago", "Xh ago", "Xd ago", "Xmo ago". No year bucket because deploys older than ~12 months are an edge nobody cares about.

statusBadge(status)

const statusBadge = (status: DeployStatus) => {
    if (status === DeployStatus.Ready)      return <Badge variant="success" />
    if (status === DeployStatus.Deprecated) return <Badge variant="warning" />
    return <Badge variant="error" />;
};

1.13 Download flow

The handleDownload(d) function decides at runtime whether the deploy has a live Blob URL or needs a synthesized fallback:

const handleDownload = (d: DeployInterface) => {
    if (d.download_url) {
        // In-session upload: re-deliver the real file
        const a = document.createElement("a");
        a.href = d.download_url;
        a.download = d.file_name;
        document.body.appendChild(a);
        a.click();
        document.body.removeChild(a);
        return;
    }
    // Seed entry or post-refresh entry: synthesize a placeholder
    const blob = new Blob(
        [`# ${d.title} ${d.version ?? ""}\n\nDemo download — backend integration pending.\n`],
        { type: "text/plain" }
    );
    const url = URL.createObjectURL(blob);
    // …same anchor-click pattern, with `.txt` extension
    URL.revokeObjectURL(url);
};

Net result: the Download button always delivers a file. Seeded entries hand you a stub .txt; in-session uploads hand you the original.

2.8 Urgency model

The entire visual identity of every card is driven by two helper functions.

daysUntil(iso): number

const daysUntil = (iso: string): number => {
    const target = new Date(iso);
    target.setHours(23, 59, 59, 999);   // end-of-day so today is day 0, not -1
    const now = new Date();
    return Math.ceil((target.getTime() - now.getTime()) / DAY_MS);
};

The setHours step makes "expires today" actually return 0, not -1 if the user opens the page at noon. Math.ceil means a reminder 1.4 days away rounds to 2, not 1 — biases toward "more time" so urgency is never overstated.

Returns a struct with tone, label, color (text class), ring (bg class for the rail), border (hover border), progress (color for progress bars), and glow (drop-shadow class, only set for high-urgency states).

const labelFor = (days: number): string => {
    if (days === 1) return "1d";
    if (days < 7) return `${days}d`;       // 2d, 3d
    if (days === 7) return "1w";
    if (days === 14) return "2w";
    if (days % 7 === 0 && days < 30) return `${days / 7}w`;
    if (days === 30) return "1m";
    return `${days}d`;                       // custom days
};

2.10 Auto-expiration logic

Reminders past their expiry should appear as Expired even if the stored status is still Active. This is an annotation, not a persisted change — important for UX rationale below.

Annotation pipeline

const annotated = useMemo(() => {
    return reminders.map((r) => {
        const days = daysUntil(r.expires_at);
        const isExpired = days < 0;
        const effectiveStatus =
            isExpired && r.status === ReminderStatus.Active
                ? ReminderStatus.Expired
                : r.status;
        return { ...r, _days: days, _status: effectiveStatus };
    });
}, [reminders]);

Why not just mutate the store? Because the user might extend the expiry date later — bumping expires_at back into the future. If we'd flipped the stored status to Expired, the reminder would stay flagged expired until manually reactivated. By keeping the stored status as Active and computing _status on render, the system "heals" automatically when the date is changed.

The annotated array (carrying _days and _status) flows through every filter, sort, and rendering decision. The raw reminders array is never read directly by the view.

2.16 Store

File: src/store/reminders.ts. Zustand store with full CRUD.

interface RemindersStore {
    reminders: ReminderInterface[];
    addReminder: (payload, by) => ReminderInterface;
    updateReminder: (id, patch) => void;
    removeReminder: (id) => void;
    setStatus: (id, status) => void;
}

addReminder

Generates an id, sets status: Active, sets created_at: new Date().toISOString(), sorts notify_before_days descending, prepends to the array, returns the new entry. Also coerces description ?? null for consistency with the seeded shape.

updateReminder

Patches the matching entry. Handles two special fields:

  • If notify_before_days is in the patch, it's re-sorted descending.
  • If description is in the patch, it's coerced from undefined to null.

setStatus

Convenience for the Dismiss / Reactivate flow — just sets the status without touching anything else.

  • BellRing — visually distinct from Bell (already used by Alerts) but in the same icon family, so users intuitively associate it with notifications.

3.4 Theming & visual conventions

  • Both modules use only the existing Tailwind theme tokens — primary, success, warning, error, text-dark, text-muted, text-faint, card, border, muted. No module-specific design tokens defined.
  • Tabular numerals (font-variant-numeric: tabular-nums) on every numeric display — counters, sizes, days-until — so digits don't jitter as values change.
  • Mono font for file names, version strings, and intervals.
  • 10pt uppercase 0.12em-tracked labels for tiny meta lines, consistent with the editorial direction set elsewhere in the dashboard.

3.5 Animations & transitions

All animations are CSS-only and GPU-composited:

  • Drop-zone state changes — transition-all duration-200
  • Card hovers — transition-colors (for border tint) and transition-all duration-200 (when card translates)
  • Changelog expand — height not animated (preserves layout stability); only the chevron rotates via transition-transform
  • Dialog open/close — managed by the underlying Radix Dialog primitive; default fade + scale

3.6 Accessibility

  • Every icon-only button has an aria-label (Download, Delete, Remove file, etc.).
  • Status tabs and select widgets use the existing Radix primitives — full keyboard nav and screen-reader semantics inherited.
  • The drop-zone fallback is always a real <input type="file">; users without drag-and-drop support (keyboard / assistive tech) can still upload.
  • Color is never the only signal: every urgency state in Reminders also has a text label (TODAY, CRITICAL, THIS WEEK, …) and a distinct numeric.

3.7 Permissions

Both modules currently route create/delete gating through p.tasks.create() — a deliberate stand-in. The proper fix when backend ships:

  1. Add policy predicates: p.deploys.create(), p.deploys.delete(), p.reminders.create(), p.reminders.edit(), p.reminders.delete().
  2. Update the two views to use the new predicates.
  3. Per the project's permission strategy: components hide rather than disable for missing permissions (with the existing exception of viewer-on-own-profile).

Part 04

Backend integration roadmap

What needs to ship server-side for each module to graduate from "UI complete" to "production".

4.1 Deploys endpoints (proposed)

MethodEndpointPurpose
GET/api/deploysList, paginated, filterable by environment, status, uploaded_by, search.
POST/api/deploysMultipart upload — file + JSON metadata (title, version, environment, changes[]).
GET/api/deploys/{id}Detail.
GET/api/deploys/{id}/downloadStream the binary, or 302 to a signed S3/R2/GCS URL.
PATCH/api/deploys/{id}/statusChange status (mark deprecated / rolled_back). Optional.
DELETE/api/deploys/{id}Permanent delete. Admin only.

Side effects

  • Notify managers on every successful POST. Likely an internal event the existing Alerts/Notifications pipeline already handles — needs the deploy-uploaded event type added.
  • Object storage — files go to S3/R2/GCS with a signed-URL download flow. The frontend's download_url field becomes the signed URL returned by the list endpoint.
  • Antivirus / scanning — uploads should be scanned before being downloadable. Hide cards with status scanning or quarantined from non-admins.
  • Size enforcement — the 250 MB UI cap is advisory; the backend should enforce real limits per environment.

4.2 Reminders endpoints (proposed)

MethodEndpointPurpose
GET/api/remindersList, paginated, filterable by status, urgency, search.
POST/api/remindersCreate. Body: { title, description, expires_at, notify_before_days[] }.
GET/api/reminders/{id}Detail.
PUT/api/reminders/{id}Full update.
PATCH/api/reminders/{id}/dismissSet status to dismissed.
PATCH/api/reminders/{id}/reactivateSet status to active.
DELETE/api/reminders/{id}Delete.

Scheduler

  • A background job (cron, BullMQ, Sidekiq) runs daily and finds every reminder where expires_at − today equals any value in notify_before_days. Each match fires a notification.
  • The same job promotes active reminders past their expiry to expired server-side, so the frontend's auto-annotate can be removed.
  • Notifications go to the reminder's created_by user. Optionally extendable to team-wide alerts.

4.3 Migration sequence

Both modules follow the established pattern used by auth, users, projects, sprints, blockers, decisions, etc.

  1. Add endpoint paths to src/data/apis.ts under deploys and reminders keys.
  2. Create src/services/deploys/index.ts and src/services/reminders/index.ts with one handler per endpoint, returning typed responses.
  3. Add domain hooks: useDeploysList, useCreateDeploy, useDeleteDeploy, useRemindersList, useCreateReminder, useUpdateReminder, useRemoveReminder, useSetReminderStatus. Use usePaginatedQuery for the list hooks and useMutationAction for the rest — both already established primitives.
  4. Swap the views from useDeployStore / useRemindersStore to the new hooks. The component code barely changes — mostly the destructure at the top of each view.
  5. Remove the seed imports and the Zustand stores. Optionally keep the stores as a local-cache layer if optimistic mutations are desired.
  6. Add proper policy predicates (p.deploys.*, p.reminders.*) and swap the p.tasks.create() stand-ins.
  7. Wire the deploy-uploaded backend event to the existing notification system.
