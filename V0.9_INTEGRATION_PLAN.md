# Plan — v0.9 API Integration (8 sidebar modules + 2 per-entity analytics)

## Context

Backend v0.9 ships APIs for 8 sidebar pages (Delivery Analytics, Gantt, Time, Meetings, Workload, Handoffs, Ownership, Reports) and 2 per-entity analytics views (Project Analytics, Sprint Analytics). All 10 surfaces already exist on the frontend driven by seed data in `src/data/seed/`. We need to replace seed-driven rendering with real API calls, following the existing service → hook → view convention used by the 13 already-integrated modules (`auth`, `users`, `teams`, `projects`, `sprints`, `tasks`, `blockers`, `decisions`, `requirements`, `time-logs`, `comments`, `red-flags`, `alerts`, `dashboard`).

Locked-in decisions from Q&A:
- **Communication module**: not part of v0.9. Leave the existing mock view untouched.
- **`/analytics` standalone route**: keep the route. Wire it to `GET /api/sprints/{activeSprintId}/analytics` using the active sprint from `useSprintStore`. The per-sprint-card "Analytics" modal uses the same service with an explicit `sprintId`. One service, two entry points.
- **Interfaces**: rewrite shapes in `src/interfaces/*` to match API responses exactly (snake_case keys when API uses them). Views update mechanically. Seeds keep their old shapes only where still referenced by the unchanged `/communication` view.

---

## Conventions (apply to every module below)

These mirror the existing pattern; each module section will just reference them.

- **Endpoint catalog**: extend `src/data/apis.ts` with a new top-level key per module. Functions for parameterized paths, strings for static ones. Mirror naming used by `blockers`/`alerts`.
- **Service**: `src/services/<module>/index.ts` exporting `<module>Service` with `<verb>Handler` async functions. Use `apiClient` from `@/lib/axios`. Re-export from `src/services/index.ts`.
- **Types**: `src/interfaces/<module>/index.ts` for response/payload/filter interfaces, re-exported from `src/interfaces/index.ts`. Suffixes: `Interface`, `PayloadInterface`, `FiltersInterface`, `ListResponseInterface`, `DetailResponseInterface`.
- **Hooks**: `src/hooks/<module>/use-<verb>-<noun>.ts`, one hook per endpoint family. Pattern: local `data`, `loading`, `error` state; manual fetch (the codebase doesn't use TanStack Query — match existing hooks like `use-blockers-list.ts`). Re-export via `src/hooks/<module>/index.ts` and the root `src/hooks/index.ts`.
- **View**: edit the existing `src/views/<module>/index.tsx` to swap seed import for hook(s). Preserve existing UI/UX. Remove unused seed import. Loading and empty states via the existing `usePageLoader` pattern used by `analytics` / `communication`.
- **Mutations** (meetings, handoffs, ownership, features, time-logs): show toast on success/error using `sonner` — match existing dialogs (`BlockerFormDialog.tsx`).
- **Errors**: rely on the global axios interceptor for 401/422; surface 422 field errors in forms via the same util the existing form dialogs use.
- **Filters / query params**: pass via the `params` axios option, never string-concatenated.

---

## Integration waves

Sequence the work to ship value early and let later modules reuse types from earlier ones.

**Wave 1 — Data-only reads (no mutations)**: Delivery Analytics → Gantt → Workload → Project Analytics → Sprint Analytics. These all replace seed with one or two GETs; lowest risk, fastest demo.

**Wave 2 — Aggregated reads with sub-tabs**: Time, Ownership, Handoffs (read endpoints), Reports (read sections). Multiple endpoints per page but still mostly GETs.

**Wave 3 — Mutations**: Meetings (heaviest — 15 endpoints, voting, RSVP, comments, attachments), Handoffs (criteria CRUD + checks), Ownership (features CRUD + linking tasks), Time (Log Time dialog), Reports (export download).

## Per-module sections

### 1. Delivery Analytics — `/delivery-analytics`

- **apisData.deliveryAnalytics**: `composite` → `/analytics/delivery`, plus `velocity`, `throughput`, `onTime`, `health`, `friction`, `blockerTrend`, `leaderboard` (sub-endpoints — wire only `composite` first; sub-endpoints reserved if charts ever need to refresh independently).
- **Service**: `deliveryAnalyticsService.compositeHandler(filters?)`. `filters`: `{ from?, to?, project_id? }`.
- **Interface** (`src/interfaces/analytics/delivery.ts`, exports `DeliveryAnalyticsResponseInterface`): shape exactly as the API doc — `health_score`, `on_time_rate`, `throughput_per_sprint`, `blocker_resolution_avg_hours`, `velocity[]`, `throughput[]`, `on_time[]`, `friction_sources[]`, `blocker_trend[]`, `leaderboard[]`. Replaces existing `DeliveryAnalyticsInterface` (rename, update barrel).
- **Hook**: `use-delivery-analytics.ts`.
- **View**: `src/views/delivery-analytics/index.tsx` — drop `analyticsSeed.delivery`. Map old field names (`velocity_history` → `velocity`, etc.) to API names. Add a small filter bar (date range, project) populated from `useProjectsList`.

### 2. Gantt — `/gantt`

- **apisData.gantt**: `tasks` → `/gantt/tasks`.
- **Service**: `ganttService.tasksHandler(filters?)`. `filters`: `{ project_id?, status?, from?, to? }`.
- **Interface** (`src/interfaces/gantt/index.ts`): rewrite to `GanttResponseInterface = { summary, tasks: GanttTaskInterface[] }`. `GanttTaskInterface`: `id, title, project_name, status, assignee_name, start_date, end_date, progress, is_delayed`.
- **Hook**: `use-gantt-tasks.ts`.
- **View**: replace `ganttSeed` import. The existing `GanttFilters` component sends the right filters; just wire its state into the hook's params. `GanttChart.tsx` field renames: `name` → `title`, `assignee.full_name` → `assignee_name`, status enum mapping (`Completed`/`InProgress`/`Delayed`/`NotStarted` → API's `completed`/`in_progress`/`delayed`/`not_started`); update `constants.ts` enum mapping accordingly.

### 3. Time — `/time`

- **Services**:

  - `timeLogsService.createStandaloneHandler(payload)` — add to existing `src/services/time-logs/index.ts`.
- **Interfaces** (`src/interfaces/time/`):
  - `TimeAggregationResponseInterface<T>` generic shape `{ summary, data: T[] }`.
  - `TimeByProjectRowInterface`, `TimeBySprintRowInterface`, `TimeByTeamRowInterface`, `TimeByMemberRowInterface`.
  - `CreateStandaloneTimeLogPayloadInterface`: `{ date, hours, user_id, project_id, sprint_id?, task_id?, note? }`.
- **Hooks**: `use-time-by-project.ts`, `use-time-by-sprint.ts`, `use-time-by-team.ts`, `use-time-by-member.ts`, `use-time-summary.ts`, `use-create-standalone-time-log.ts`.
- **View**: tabs (Projects/Sprints/Teams/Members) each call their own hook on mount/tab change. `LogTimeDialog.tsx` — switch between `timeLogsService.createHandler(taskId, ...)` and `createStandaloneHandler(...)` depending on whether a task is selected. yup validation: `hours` min 0.25, max 24; `date` required; `user_id`/`project_id` required.

### 4. Meetings — `/meetings` (largest module)

- **apisData.meetings**: `list`, `listLite`, `create`, `detail(id)`, `update(id)`, `delete(id)`, `addSlot(id)`, `removeSlot(id, slotId)`, `vote(id, slotId)`, `finalize(id)`, `rsvp(id, userId)`, `commentsList(id)`, `commentCreate(id)`, `commentDelete(id, commentId)`, `attachmentUpload(id)`, `attachmentDelete(id, attachmentId)`.
- **Service**: `meetingsService` — one handler per endpoint. `uploadAttachmentHandler` uses `FormData` with `multipart/form-data` Content-Type; reference how task attachments are sent (`src/services/tasks/index.ts`).
- **Interfaces** (`src/interfaces/meetings/`): rewrite to match API doc — `MeetingListItemInterface`, `MeetingDetailInterface` (with nested `project`, `team`, `organizer`, `time_slots[]`, `attendees[]`, `comments[]`, `attachments[]`), `MeetingTimeSlotInterface`, `MeetingAttendeeInterface { user_id, name, role, rsvp_status, voted_slot_id }`, `MeetingCommentInterface`, `MeetingAttachmentInterface`, `CreateMeetingPayloadInterface`, `UpdateMeetingPayloadInterface`, `MeetingsListFiltersInterface { status?, from?, to?, search?, page? }`, paginated `MeetingsListResponseInterface { data, meta }`.
- **Hooks**: `use-meetings-list`, `use-meetings-list-lite`, `use-meeting-detail`, `use-create-meeting`, `use-update-meeting`, `use-delete-meeting`, `use-add-meeting-slot`, `use-remove-meeting-slot`, `use-vote-meeting-slot`, `use-finalize-meeting`, `use-update-meeting-rsvp`, `use-meeting-comments`, `use-create-meeting-comment`, `use-delete-meeting-comment`, `use-upload-meeting-attachment`, `use-delete-meeting-attachment`.
- **View**:
  - `src/views/meetings/index.tsx`: list + filters via `useMeetingsList`. Tabs "Upcoming"/"Past" use server-side `from`/`to` filters around today.
  - `RequestMeetingDialog.tsx`: send full `CreateMeetingPayloadInterface` including `attendee_ids[]` and `time_slots[]`. Validate ≥1 slot.
  - `MeetingDetail.tsx`: vote/RSVP/comment/attachment actions call respective hooks; optimistic update of `votes_count` and `voted_slot_id` after vote success; refetch detail after `finalize`.
- **Permissions** (per doc, enforced in UI affordances): hide Delete button unless user is organizer or admin; hide Finalize unless organizer/admin/manager.

## Cross-cutting work

- **Permissions in UI**: the API enforces RBAC, but to avoid showing dead buttons, gate destructive/manager-only affordances using `useAuthStore().user.role`. Helper `canManage(roles: string[])` in `src/lib/permissions.ts` (new). Apply to: Meetings (delete/finalize), Handoffs (manage criteria), Ownership (create/edit/delete features), Reports (export — viewers blocked).
- **Routes**: no new routes needed — all 10 surfaces already exist. The two per-entity analytics views are already wired as modals on project/sprint cards.
- **Sidebar**: no changes; entries already exist.
- **Seed cleanup**: once a module is integrated and verified, delete its seed file (`src/data/seed/<module>.ts`) and remove the import line from `src/data/seed/index.ts`. Keep `time.ts` until `/communication` is migrated (it references members/teams indirectly).
- **Type churn**: search-replace old interface names after rewrites. Run `tsc -b` after each module to catch consumers.
- **Empty states / loading**: reuse the `usePageLoader` + skeleton patterns already in `analytics` and `communication` views.
- **Toasts**: `sonner.success` on mutations, `sonner.error` from caught axios errors. The interceptor already extracts the user message.

## Verification

Per-module smoke test after integration (manual, in dev):
1. `pnpm dev` → log in.
2. Visit the route, confirm network request fires against `https://pm-bck.twindix.com/api/<endpoint>` with `Authorization: Bearer ...`.
3. Confirm data renders, no console errors, no TypeScript errors (`pnpm tsc -b`).
4. Exercise filters/tabs — confirm query params hit the network.
5. For mutation modules: create/edit/delete one item, confirm toast + UI update + 200 response.
6. For modals (Project Analytics, Sprint Analytics): open from a project/sprint card, confirm data loads.
7. For Reports export: trigger PDF and Excel export, confirm file downloads with correct content-type.
8. Permissions: log in as a viewer (if a test account exists) and confirm manager-only buttons hidden.
9. After all modules in a wave land: `pnpm build` to ensure type-check + bundle succeed.

Acceptance per module covered by the API doc's "Testing Requirements" section — use it as a checklist before marking each module done.
